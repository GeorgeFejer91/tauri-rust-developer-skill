# Plugin Selection and Development

Use this guide when installing, evaluating, authoring, testing, or publishing a Tauri plugin.

## Select a Plugin

1. Prefer Tauri's maintained plugin set when it meets the requirement.
2. For community plugins, inspect source, recent releases, issues, license, supported Tauri major version, desktop/mobile matrix, permissions, scopes, native dependencies, and maintainer activity.
3. Read `permissions/default.toml` and autogenerated command permissions before installation.
4. Add only the Rust and guest-language packages actually used, preserving the repository's package manager.
5. Initialize once and compile immediately before adding frontend calls.

The Tauri CLI can add supported official plugins and update capability plumbing, but inspect every generated change. A successful install does not prove appropriate authority.

## Plugin Shape

A full plugin can contain:

- a Rust crate with commands, state, platform dispatch, errors, and permission generation;
- a guest-JavaScript/TypeScript package with typed wrappers;
- Android and iOS native implementations;
- examples, permission schemas, and tests.

Keep the guest API small and typed. Exporting a friendly wrapper has no security effect: the registered invoke handler and Tauri authority model determine reachability.

## Commands and Permissions

- Register plugin commands in the plugin builder.
- List commands in the build script's command set so Tauri generates matching allow/deny permissions.
- Keep command names and guest invoke names synchronized, including `plugin:name|command` conventions and camelCase serialization.
- Put only low-risk, expected behavior in the plugin's default permission set. Privileged write, shell, process, network, camera, or broad filesystem operations should require explicit opt-in.
- Add hand-written permission sets for coherent use cases rather than forcing apps to assemble dozens of internal commands.
- Add scopes when enabled commands need resource constraints.

Do not copy tutorial examples blindly. Validate file destinations, avoid panic/unwrap, sanitize responses, and never render arbitrary command output as HTML.

## Scoped Commands

For a plugin scope:

1. define serializable allow/deny scope entries and generate their schema;
2. expose the scope through the permission manifest;
3. resolve the caller's command scope in Rust;
4. canonicalize and compare the requested resource;
5. enforce deny entries and default behavior explicitly;
6. test allowed, denied, missing, malformed, and platform-specific cases.

Keep scope types available to both build-time schema generation and runtime code without duplicating their definition.

## Mobile Bridges

Keep a platform-neutral Rust API and map it to Kotlin/Swift implementations. Validate native-thread requirements, permission prompts, activity/scene lifecycle, serialization, and error mapping. Never assume a desktop-only crate or API can compile on mobile.

If native code calls shared Rust through JNI or FFI, keep the ABI surface tiny, validate every pointer/string/length, prevent unwinding across the boundary, define ownership and thread affinity, and compile/test every advertised architecture. Do not assume the WebView is alive when a background native callback arrives; queue, persist, or route through lifecycle-aware state as the product requires.

## Tests and Release

- unit-test platform-neutral Rust logic;
- test permission generation and generated schemas;
- use the generated example application for integration tests;
- build the guest package and verify its declarations and type output;
- compile each advertised target and run native-device tests where applicable;
- document permissions, scopes, platform differences, and migration notes;
- publish crates/npm packages or tags only with explicit authorization.
